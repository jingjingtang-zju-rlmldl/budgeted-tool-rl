# 下一阶段：完整工具轨迹 SFT 小实验

这是一份依据提示对照结果制定的待执行方案。本轮未开始训练。目标是让模型完成两步查询并依据当前工具观测回答，而不是仅提高已经能由示例解决的 JSON 格式分数。

## 先固定数据和对照

先修正生成器，使项目和员工使用独立随机 ID，owner 关系只能从工具查得。训练、开发、测试的实体与私有值来源分开；按数据库实体划分，避免同一事实在不同划分重复出现。保留原 100 题和本轮 60 题作为历史诊断，不把它们改名为独立测试集。

重新生成开发集与独立模板测试集，再跑 base + 短中性提示、base + 系统内平衡示例。独立模板在选训练参数前固定，不用于提示选择或 checkpoint 选择。当前最强的提示基线必须纳入比较，否则“训练后 JSON 更好”可能只是漏掉提示工程对照。

训练从 **300 个任务轨迹**开始：直接回答、一次查询、两次查询各 100 个。其中部分预算题与部门题使用同一训练数据库形成目标对照，让相同实体在不同问题下选择不同字段。训练事实不能跨划分。采用更多措辞，测试保留独立模板族。

## 标签与训练单位

由确定性 oracle 执行真实环境，先验证工具结果和最终答案，再导出正确轨迹。失败的 baseline 输出用于诊断，不直接作为正确 SFT 标签。工具观测通过实际 lookup 生成，不将隐藏数据库、expected 或 oracle 路径直接塞进模型问题。

每个模型决策以“系统协议 + 当前问题 + 已发生的动作和工具结果”为输入，监督下一条 assistant JSON 动作及结束 token。用户、系统、工具观测 token 不计入损失。300 条完整轨迹对应约 **600 个 assistant 决策目标**，包括 100 个需要在 owner 观测后继续查 department 的关键状态。

优先使用短中性提示训练与推理，避免模型依赖长示范中的固定答案。必须核验输入 token 与推理模板一致、标签 mask 对齐、EOS 正确；训练时出现的工具观测保持冻结，只监督模型动作。保留逐请求监督状态，便于检查中间状态是否被遗漏。

## 算力与初始配置

先在 5060 上做 5–10 个真实 forward / backward / optimizer 步，记录峰值 allocated/reserved、吞吐、损失是否有限以及可训练参数数目。推理的 1.28 GiB 峰值不能代替该测量。

可从 BF16、LoRA rank 8、attention 的 q/v 投影、micro-batch 1、梯度累积 8、上下文上限 768、学习率 1e-4、1 个 epoch 起步。这些是待验证的起点，不是已经调优或保证能装下的配置。先统计训练样本长度，不静默截断；显存不足时再启用梯度检查点或缩短实际样本，而不是假定必需云端 A100。

先跑单种子小实验，依据开发集挑 checkpoint；若有收益，再重复训练种子验证稳定性。所有训练参数、源码、数据哈希和 adapter 都应保存，不把一次偶然成功当作稳定收益。

## 怎么评估是否值得继续

| 条件 | 用途 |
|---|---|
| base + 短中性提示 | 与训练后同接口对比 |
| base + 系统内平衡示例 | 最强提示对照 |
| SFT + 短中性提示 | 检验是否学会在短输入下执行目标 |
| SFT + 平衡示例 | 检查权重收益是否还能叠加提示收益 |

对各条件使用一致的采样配置、任务与评测种子。报告两步最终正确率、正确的首个查询、第二次查询是否使用实际 owner 结果、过早回答比例、示例值照抄、严格协议成功率，以及正确性条件下的调用数。既报告兼容解析，也保留严格 JSON 分数。

开发集上可将“两步成功达到 80%、直接回答与一次查询保持至少 95%”设为工程验收目标；它们是目标，不是预言或已取得成绩。冻结 checkpoint 后仅按预定流程评估独立模板测试集，不能用测试分数继续挑选模型。

如果只在已见措辞上改善，先补数据和模板多样性。如果只是 JSON 改善，而两步仍为零，检查关键中间状态的标签和目标保持，不急于加 RL。若 SFT 出现稳定的真实两步成功，再观察多次 rollout 的成功/失败混合情况，决定是否做正确性奖励的 GRPO。

当前正确轨迹已无多余调用；成本奖励应留到有真实冗余机会的更复杂任务。若 SFT 在简单任务上已经全对，也需要增加困难任务形成可学习的差异，才能公平评估 RL 是否提供额外收益。
