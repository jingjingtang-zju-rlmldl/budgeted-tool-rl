# 提示对照结论与 SFT 决策

**提示能够改善格式、单步查询和多步查询的启动，但本轮四种配置都没有完成两步目标。建议做完整动作轨迹的 LoRA SFT 小实验，保留最有效的提示作为强基线。** 这表明当前策略在该任务上不稳定，不证明 0.6B 模型的能力上限，也不能排除其他提示或 thinking 配置有效。

60 个新任务，直接回答、一次查询、两次查询各 20 个；每组重复三个种子，共 720 次真实 CUDA 任务尝试。每一格的 60 次尝试是 20 题 × 3 种子，不是 60 个独立任务。原提示、中性提示、系统内平衡示例是实验前固定的主对照；对话形式示例是看过首轮结果后追加的探索对照，两者分别保存方案和记录。

| 提示 | 直接回答 | 一次查询 | 两次查询 | 总体正确率 | 全程严格 JSON 且正确 |
|---|---:|---:|---:|---:|---:|
| 原提示 | 60/60 | 55/60 | 0/60 | 115/180，63.9% | 13/180，7.2% |
| 中性提示 | 60/60 | 44/60 | 0/60 | 104/180，57.8% | 25/180，13.9% |
| 系统内平衡示例 | 60/60 | 60/60 | 0/60 | 120/180，66.7% | 120/180，66.7% |
| 对话形式示例（追加） | 60/60 | 0/60 | 0/60 | 60/180，33.3% | 60/180，33.3% |

主要分数仅允许剥离完整单个 Markdown 围栏；没有修复内容、强制解码或失败重试。原始请求 JSON 合规率分别为 63/238（26.5%）、83/224（37.1%）、278/278（100%）、159/180（88.3%）。因此格式合规与任务完成必须分开报告。

## 这些结果支持什么

中性提示只删除具体的 owner→department 路径描述。它没有恢复两步成功，且相同题目与种子的成对比较中，2 次由失败变成功、13 次由成功变失败。当前证据不支持“删除那段提示即可解决”的推测。上轮预算题误走 owner 路径的现象，本轮原提示未复现（0/60），不能把上轮个例当成稳定机制。

系统内平衡示例使一次查询从 55/60 提升到 60/60，所有请求直接输出合法 JSON。两步题有 38/60 启动查询，说明动作选择对提示敏感，但没有一次执行第二次查询；38 次只查一步，22 次不查。28 次最终答案照抄示例部门 `department_48216`，25 次返回员工 ID，而非问题要求的部门。这两个答案类别互斥，剩余失败还有其他错误答案。

对话示例组三个种子均为 20/60 正确，没有任何当前任务的工具调用；出现复用示例预算、部门值，或将实体后缀当作预算。该形式在本模型和协议上更差。它同时改变角色表示与示例边界措辞，所以不能将差异完全归因于角色标签。

可操作的判断是：**当前较强提示已经解决这批任务的单步和格式问题；尚待学习的是保持当前目标、将工具观测视为中间状态、继续查询、以及依据当前事实结束任务。** 模型在旧 baseline 的错误预算轨迹中曾产生连续调用，因此不能笼统说它完全无法调用两次。

## 方法、资源和复核

固定 Qwen3-0.6B snapshot、BF16、SDPA、batch 1、关闭 thinking、temperature 0.7 / top-p 0.8 / top-k 20；各组共享问题、事实和任务种子。最长 oracle 上下文分别为 437、414、752、736 token，低于统一的 1,024 上限；生成上限 64 token，最多 3 次调用 / 4 次生成。所有组都没有 context_limit 或 generation_truncated。三个主对照的执行顺序随种子轮换。

累计模型推理 1,368.78 秒，约 22 分 49 秒，不含模型加载、复核和文档工作。最大 PyTorch CUDA allocated 为 1,315.78 MiB，约 1.28 GiB，没有 OOM；桌面其他负载未关闭，不能据此比较各提示的纯硬件速度，也不能推断训练显存。

720 条轨迹、920 次模型请求均已独立重建输入 token、解码输出、回放工具并重新判分。示范是手写提示材料，不计作真实模型生成或当前工具调用。原 baseline/environment 源码没有修改；wrapper 的进程内提示替换、对话示范前缀及其哈希另行记录。复核器支持实际问题的位置索引，以核验包括示范在内的完整模型输入。

环境与分析的 20 个单元测试通过。归档检查还修正了数据生成器在 Windows 上的换行哈希记账：旧数据 manifest 的 sha256 使用 LF 规范化文本，现改为实际文件字节哈希并保留 normalized_lf_sha256，审计见 [dataset-manifest-hash-correction.json](dataset-manifest-hash-correction.json)。任务文件字节没有改动；所有执行 manifest 和实验 plan 原本就使用实际字节哈希，评分与复核结果不受影响。新生成数据显式使用 LF，避免再次发生这种差异。

[主对照明细与复现命令](metrics.zh-CN.md)、[主对照数值](summary.json)、[主对照预定方案](plan.json)、[追加对照数值](../native-examples-v1/summary.json)、[追加对照方案](../native-examples-v1/plan.json)均已保存，各运行目录包含完整原始轨迹与 verification。

本轮是合成英文任务、既有模板族、新实体的开发诊断，没有模板外或真实生产任务证据。还有一个需要在训练前修正的数据设计问题：当前项目与员工 ID 共享后缀，可能暴露关系结构；应改为独立随机 ID，再建立新的基线和训练评测集，不能把 oracle 的两步路径无条件称为信息论上的最少调用数。
